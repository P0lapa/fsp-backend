# Дизайн: задачи, наборы задач и их привязка к турнирам

## Контекст

В проекте уже существует сущность турнира (`Contest`). Нужно добавить поддержку задач и наборов задач так, чтобы:

- задачи могли существовать самостоятельно;
- наборы задач могли существовать самостоятельно и переиспользоваться;
- турнир в пользовательском сценарии мог сначала создаваться как черновик;
- турнир нельзя было перевести из `DRAFT` в любой другой статус без привязанного набора задач;
- организатор мог либо выбрать готовый набор задач, либо создать свой набор, наполнить его задачами и затем привязать к турниру.

Это означает, что строгая обязательность набора задач для турнира должна обеспечиваться бизнес-правилом, а не обязательным `NOT NULL` полем в таблице турниров. Иначе сценарий черновика ломается.

## Цели

- Добавить сущность задачи со всеми базовыми полями условия и ограничений.
- Добавить сущность набора задач, доступную для повторного использования.
- Добавить состав набора задач с порядком, буквенным обозначением и баллами.
- Добавить связь набора задач с турниром.
- Поддержать два сценария:
  - привязка уже существующего набора к турниру;
  - создание турнира, затем создание собственного набора и его привязка.

## Не цели MVP

- Версионирование задач и наборов задач.
- История изменений состава набора.
- Поддержка нескольких наборов задач в одном турнире одновременно.
- Поддержка архивных снимков набора задач на момент старта турнира.
- Полноценная авторизационная модель на уровне отдельных задач и наборов сверх базового признака публичности и автора.

## Предметная модель

### Task

Самостоятельная задача с полным описанием условия.

Поля:

- `id`
- `title`
- `shortName`
- `statement`
- `inputDescription`
- `outputDescription`
- `notes`
- `exampleInput`
- `exampleOutput`
- `constraintsText`
- `timeLimitMs`
- `memoryLimitMb`
- `source`
- `authorUserId`
- `isPublic`
- `createdAt`
- `updatedAt`

Особенности:

- задача может существовать без набора задач;
- одна и та же задача может использоваться в нескольких наборах;
- `authorUserId` заполняется на бэке по текущему пользователю.

### ProblemSet

Самостоятельный набор задач, который организатор может подготовить заранее и затем переиспользовать.

Поля:

- `id`
- `title`
- `description`
- `createdByUserId`
- `isPublic`
- `createdAt`
- `updatedAt`

Особенности:

- набор задач может существовать без турнира;
- набор задач может быть использован повторно в разных турнирах;
- состав набора хранится отдельно через `ProblemSetTask`.

### ProblemSetTask

Связь задачи с набором задач.

Поля:

- `id`
- `problemSetId`
- `taskId`
- `orderNum`
- `contestLabel`
- `score`

Особенности:

- одна запись соответствует одному включению задачи в конкретный набор;
- `orderNum` задает порядок показа задач в наборе;
- `contestLabel` задает буквенное обозначение внутри набора, например `A`, `B`, `C`;
- `score` хранится даже если в MVP для ICPC фактически не используется.

### ContestProblemSet

Связь турнира с набором задач.

Поля:

- `id`
- `tournamentId`
- `problemSetId`

Особенности:

- на уровне таблицы используется отдельная сущность связи, как в исходном требовании;
- на уровне бизнес-логики в MVP у одного турнира допускается только один активный набор задач;
- повторная привязка набора к турниру заменяет текущую связь, а не создает множество активных связей.

### Contest

Текущая сущность турнира сохраняется, но меняются правила жизненного цикла:

- турнир можно создать без набора задач только как `DRAFT`;
- турнир без набора задач нельзя перевести в любой статус, отличный от `DRAFT`;
- публичный турнир без набора задач запрещен;
- турнир считается готовым к публикации только после привязки набора, содержащего минимум одну задачу.

## Почему обязательность через бизнес-правило, а не через `NOT NULL`

Если сделать обязательный `problemSetId` прямо в турнире, то фронтовый сценарий "создать турнир -> спросить про готовый или новый набор -> наполнить набор -> привязать набор" станет невозможен. Поэтому в модели данных допускается отсутствие привязанного набора только для черновика. Обязательность набора обеспечивается при смене статуса и публикации турнира.

## Структура данных в JPA

Предлагаемая модель сущностей:

- `TaskEntity`
- `ProblemSetEntity`
- `ProblemSetTaskEntity`
- `ContestProblemSetEntity`
- существующий `ContestEntity`

Связи:

- `ProblemSetTaskEntity` -> many-to-one к `ProblemSetEntity`
- `ProblemSetTaskEntity` -> many-to-one к `TaskEntity`
- `ContestProblemSetEntity` -> many-to-one к `ContestEntity`
- `ContestProblemSetEntity` -> many-to-one к `ProblemSetEntity`

Для MVP не требуется двусторонняя навигация во всех направлениях. Лучше держать связи простыми и читать состав набора/связь турнира через отдельные репозитории и сервисы.

## Ограничения и инварианты

### Для задач

- `title` обязателен;
- `shortName` обязателен;
- `statement` обязателен;
- `timeLimitMs` должен быть положительным;
- `memoryLimitMb` должен быть положительным;
- `isPublic` обязателен;
- `authorUserId` выставляется на бэке и не принимается от клиента.

### Для наборов задач

- `title` обязателен;
- `isPublic` обязателен;
- `createdByUserId` выставляется на бэке;
- набор может быть пустым во время создания, если пользователь еще только собирает его;
- перед привязкой к турниру набор обязан содержать минимум одну задачу.

### Для состава набора

Внутри одного `problemSetId`:

- `orderNum` должен быть уникальным;
- `contestLabel` должен быть уникальным;
- одна и та же задача не должна добавляться повторно;
- `score`, если задан, должен быть неотрицательным.

### Для связи турнира и набора

- в MVP на один турнир допускается только одна запись активной связи;
- привязать к турниру можно только существующий набор;
- привязать к турниру можно только набор, содержащий минимум одну задачу;
- если набор уже привязан, новая привязка заменяет текущую.

### Для турнира

- создание турнира без набора задач разрешено только в статусе `DRAFT`;
- перевод турнира из `DRAFT` в любой другой статус без набора задач запрещен;
- установка `isPublic = true` без набора задач запрещена;
- удаление привязанного набора задач должно либо запрещаться, либо предварительно требовать отвязки от турнира; для MVP предпочтительно запрещать удаление, если набор связан с турниром не в `DRAFT`.

## API

### Турниры

#### `POST /api/contests`

Создает турнир.

Поведение:

- если `problemSetId` не передан, создается турнир в `DRAFT`;
- если `problemSetId` передан, создается турнир и сразу создается связь с набором;
- если `problemSetId` не передан и клиент пытается создать турнир не в `DRAFT`, запрос отклоняется;
- если `problemSetId` передан, но набор пустой, запрос отклоняется.

Рекомендуемое решение для DTO:

- оставить `ContestRequestDto` только для полей самого турнира;
- добавить опциональное поле `problemSetId`, если нужна поддержка одномоментной привязки при создании;
- не включать в DTO турнира состав задач или данные нового набора, чтобы не смешивать разные агрегаты.

#### `PUT /api/contests/{id}`

Обновляет поля турнира.

Поведение:

- если статус остается `DRAFT`, обновление возможно без набора;
- если клиент пытается перевести турнир в статус, отличный от `DRAFT`, сервис обязан проверить наличие привязанного набора;
- если клиент пытается сделать турнир публичным без набора задач, запрос отклоняется.

#### `PUT /api/contests/{id}/problem-set`

Привязывает существующий набор задач к турниру.

Тело запроса:

- `problemSetId`

Поведение:

- если у турнира нет связи, она создается;
- если связь уже есть, она заменяется;
- привязываемый набор обязан содержать хотя бы одну задачу.

#### `GET /api/contests/{id}`

Возвращает турнир.

Поведение:

- в полном ответе возвращается краткая информация о привязанном наборе задач, если он есть;
- по желанию можно возвращать и количество задач в наборе.

### Наборы задач

#### `POST /api/problem-sets`

Создает новый набор задач.

Поведение:

- набор может быть создан пустым;
- `createdByUserId` определяется по текущему пользователю.

#### `GET /api/problem-sets`

Возвращает список доступных наборов задач.

Для MVP достаточно:

- публичные наборы;
- собственные наборы текущего пользователя.

#### `GET /api/problem-sets/{id}`

Возвращает метаданные набора и его состав.

#### `PUT /api/problem-sets/{id}`

Обновляет название, описание и публичность набора.

### Состав набора задач

#### `POST /api/problem-sets/{id}/tasks`

Добавляет задачу в набор.

Тело запроса:

- `taskId`
- `orderNum`
- `contestLabel`
- `score`

#### `PUT /api/problem-sets/{id}/tasks/{linkId}`

Обновляет связь задачи с набором.

Поведение:

- можно менять порядок;
- можно менять буквенное обозначение;
- можно менять баллы;
- при необходимости можно заменить `taskId`.

#### `DELETE /api/problem-sets/{id}/tasks/{linkId}`

Удаляет задачу из набора.

### Задачи

#### `POST /api/tasks`

Создает самостоятельную задачу.

#### `GET /api/tasks`

Возвращает список задач.

Для MVP достаточно:

- публичные задачи;
- собственные задачи текущего пользователя.

#### `GET /api/tasks/{id}`

Возвращает полное описание задачи.

#### `PUT /api/tasks/{id}`

Обновляет задачу.

## DTO

`ContestRequestDto`

- оставить поля турнира;
- добавить опциональный `problemSetId`, если нужна моментальная привязка готового набора.

`ContestFullResponseDto`

- добавить краткий объект `problemSet`;
- в краткий объект достаточно включить:
  - `id`
  - `title`
  - `description`
  - `taskCount`

`BindProblemSetToContestRequestDto`

- `problemSetId`

## Сервисный слой

Новые сервисы:

- `TaskService`
- `ProblemSetService`
- `ContestProblemSetService`

Изменения в `ContestService`:

- создание турнира должно уметь создавать черновик без набора;
- создание турнира должно уметь сразу привязывать готовый набор, если он передан;
- обновление турнира должно проверять ограничения на статус и публичность;
- получение полного турнира должно включать краткую информацию о наборе задач.

## Репозитории

Новые репозитории:

- `TaskRepository`
- `ProblemSetRepository`
- `ProblemSetTaskRepository`
- `ContestProblemSetRepository`

Рекомендуемые проверки в репозиториях:

- поиск набора по `id`;
- проверка наличия задач в наборе;
- поиск связи турнира с набором;
- проверка уникальности `orderNum`, `contestLabel` и `taskId` внутри набора;
- выборка доступных пользователю задач и наборов.

## Проверки на уровне бизнес-логики

При создании или обновлении турнира:

1. Если нет привязанного набора, статус обязан быть `DRAFT`.
2. Если нет привязанного набора, `isPublic` обязан быть `false` или запрос должен отклоняться.
3. При привязке набора нужно проверить, что он не пустой.
4. При смене набора у турнира нужно заменить старую запись связи.

При работе с набором:

1. Нельзя добавить одну и ту же задачу в набор дважды.
2. Нельзя допустить дубли `orderNum`.
3. Нельзя допустить дубли `contestLabel`.
4. Если набор уже используется турниром вне `DRAFT`, удаление состава должно либо запрещаться, либо строго валидироваться; для MVP предпочтительно запрещать такое изменение.

## Тестирование

Минимальный набор тестов:

### `ContestServiceTest`

- создание турнира без набора создает `DRAFT`;
- создание турнира с `problemSetId` создает связь;
- перевод турнира без набора из `DRAFT` в другой статус отклоняется;
- публикация турнира без набора отклоняется;
- привязка пустого набора к турниру отклоняется;
- повторная привязка набора заменяет текущую связь.

### `ProblemSetServiceTest`

- можно создать пустой набор;
- можно добавить задачу в набор;
- нельзя добавить одну и ту же задачу дважды;
- нельзя использовать дублирующий `orderNum`;
- нельзя использовать дублирующий `contestLabel`.

### `TaskServiceTest`

- задача создается с автором из текущего пользователя;
- валидация отклоняет некорректные лимиты;
- публичные и собственные задачи корректно выбираются.

### Интеграционные тесты контроллеров

- создание турнира-черновика;
- привязка существующего набора к турниру;
- создание собственного набора и наполнение задачами;
- запрет публикации турнира без набора;
- успешная публикация турнира после привязки набора.

## Риски и принятые решения

### Риск

Если разрешить редактирование набора, уже привязанного к опубликованному турниру, это может менять состав задач задним числом.

### Решение для MVP

Для MVP считать, что набор, привязанный к турниру вне `DRAFT`, редактировать нельзя. Это упрощает правила и защищает от неожиданных изменений.

### Риск

Отдельная таблица `ContestProblemSet` при отношении один-к-одному выглядит избыточной.

### Решение

Все равно использовать отдельную связь, потому что это соответствует исходному требованию и оставляет путь к расширению в будущем, если появятся несколько наборов или ревизии привязок.

## Итог

Для MVP оптимальна модель, в которой:

- задачи и наборы задач являются самостоятельными сущностями;
- турнир может существовать без набора задач только как черновик;
- обязательность набора задач обеспечивается бизнес-правилами при публикации и смене статуса;
- фронт получает удобный поток: создать турнир -> выбрать готовый набор или создать новый -> привязать набор -> опубликовать турнир.
